// 03 — how we work

The methods behind the code

Our delivery rules — these keep the product stable while several devs and AI coding sessions work in parallel.

1
Branch → gates → reviewed push
Daily work happens on the team's integration branch; exact branch and repo names live in ARCHITECTURE.md §3. Never push without explicit permission, and never push until all gates below are green.
2
Quality gates before every push
npx oxlint src → 0 errors · npm run build → OK (postbuild guards verify the API base URL and the Firebase web key in the bundle) · gradlew test → green · staged-diff secrets scan · deploy zips must pass check-zip.ps1 → ALL GREEN.
3
Backend deploys through a mirror repo
Backend code is copied into the deploy-mirror repository, pushed there, and GitHub Actions runs the test suite against an empty database before Render auto-deploys. Syncing the mirror is a permissioned step — ask before doing it.
4
Frontend ships as a gated zip
Production dist/ is zipped (forward-slash entries only — plain Compress-Archive breaks Linux unzip), gated with check-zip.ps1, then extracted into the host's public_html.
5
Migrations are append-only
New entity ⇒ new Flyway migration in the same change. Never edit an applied V* file; only R__Seed_data.sql is editable in place and must stay idempotent.
6
Design & i18n rules
Colors/spacing come from tokens.css (no hardcoded hex in new code); every user-visible string goes into all 5 language dictionaries. Product data always comes from the API, never hardcoded in components.

2

Switch the agent to the MiMo model

→ run inside the OpenCode chat

Open your project folder in OpenCode, then run the connect command and select the MiMo model (mimo-v2.6-flash-free) — the default agent for this project:

3

Read ARCHITECTURE.md in the git repository

→ repo root → ARCHITECTURE.md — read fully, it is the source of truth

Before writing any code, open the repository on GitHub (your access is granted with your account) and read the root file ARCHITECTURE.md from top to bottom. It is the single system map: tech stack (§2), repositories & branches (§3), frontend/backend structure (§4–§5), external services (§6), auth & security model (§7), country/pricing logic (§8), environments (§10), build & deploy (§12), house rules (§13), and a "which doc for what" index (§16).

If any other document disagrees with it, ARCHITECTURE.md wins. Skim once, then re-read properly — 20 minutes now saves days later. The root README.md (quick start + test credentials) and the per-area READMEs are next.

4

Get your developer access token (git push & pull)

→ GitHub → Settings → Developer settings → Personal access tokens

Git authentication on this project uses a personal access token that you generate yourself on GitHub. You paste it when git (or OpenCode acting as git) asks for credentials — it then works for both git pull and git push. Learn the generation step from this video first — click the thumbnail or the URL, both open the same video:

Token generation guide · YouTube
How to Generate a Personal Access Token in GitHub — the token you will use to push & pull
https://youtube.com/shorts/KLWsGhUUFDM?si=o1otO_0mciOui3Aq
Watch it, generate and copy your token — then come straight back here and paste that token into OpenCode when git asks for credentials (panel Ⓑ below). The token alone means nothing until it is pasted into OpenCode for your git pull / git push.

Ⓐ Generate the token (once)

  1. Sign in to GitHub → click your avatar → Settings.
  2. Bottom of the left sidebar → Developer settings → Personal access tokens.
  3. Choose Fine-grained tokens → Generate new token (or Tokens (classic)).
  4. Set an expiry (30/60/90 days). Grant repository access to the project repos. Permission needed: Contents – Read & write (classic: tick the repo scope).
  5. Click Generate token and copy it immediately — it is shown only once and looks like ghp_••••••••.

Ⓑ Paste it into OpenCode

  1. With the token copied, open your project in OpenCode and run git pull or git push (directly, or by asking the agent to do it).
  2. When credentials are requested: Username = your GitHub username, Password = paste the token into the OpenCode prompt.
  3. On Windows the credential manager stores it after the first paste — you will not retype it every time.
  4. Push failure 401/403 usually means the token expired or lacks Contents: Read & write → watch the video above and generate a new one (step Ⓐ).

⚠ Treat it like a password

  1. One token per person — never share yours with anyone, including teammates or agents.
  2. Never commit it, never paste it into source files, docs, screenshots or chat logs, and never embed it in a repository URL.
  3. If a token is ever leaked, revoke it immediately (Settings → Developer settings → Personal access tokens → Delete) and generate a replacement.
  4. Rotate before expiry; a dead token is the most common cause of sudden push errors.

→ two terminals: API on :8080, site on :5173

git clone <repository-url>   # your access, prompted once — paste the token

// 05 — non-negotiable

Security red lines

Breaking any of these is a ship-blocker, not a style preference.

  • Never commit .env files, API keys, tokens, passwords or session logs to git.
  • Your developer token is yours alone — never share it, never paste it into code, docs or screenshots.
  • No identity or order data in browser storage — sessions stay in httpOnly cookies set by the backend.
  • Never hardcode secrets into application.yml / build.gradle — environment variables only.
  • Never push without permission, and never push un-gated builds (lint/build/test/zips) to the shared branch.
  • Server recomputes all payable amounts — never trust totals sent from the client, and never expose admin keys client-side.
